# Перенос ChemMaster Assistant в клиентский мод SS14

Дата: 10 октября 2026 года. Статус: установлен ChemMaster 0.1.3 для локальной сборки ModLauncher 0.1.6: вкладки «АВТО» и «Настройки АВТО», фазы холодной/горячей мензурки и продолжение оставшейся цели. Использование и ограничения — в [документации мода](mods/chemmaster.md). Ниже сохранён архитектурный контекст исследования.

Перенос возможен через существующий SS14 ModLauncher. Рекомендуемый результат — вкладка «Рецепты» в открытом штатном химмастере: выбор препаратов, сохранение собственных наборов, расчёт ингредиентов и автоматическое выполнение через обычные сообщения игрового интерфейса. Для этого сценария серверные изменения не требуются, пока мод использует поддерживаемые сервером действия и доступные клиенту данные.

Клиент может автоматизировать производство по существующим реакциям. Пользовательский рецепт здесь означает сохранённую цель производства или смесь. Добавить новую химическую реакцию, которой нет на сервере, одним клиентским модом нельзя.

## Подключение к открытому химмастеру

В существующем лаунчере Bootstrap загружает выбранные DLL после появления `Content.Client`. Контракт мода — `SS14LocalMods.Mod.Install(Assembly content)`. Crew Console и Conversations уже показывают, как создавать нативные игровые контролы и подключать их через Harmony и reflection.

У химмастера есть следующие точки подключения:

| Точка | Использование модом |
| --- | --- |
| `ChemMasterBoundUserInterface.Open()` | Postfix получает созданное `_window` и добавляет вкладку рецептов один раз для этого экземпляра |
| `ChemMasterBoundUserInterface.UpdateState(state)` | Postfix копирует свежий состав и обновляет состояние выполнения |
| `BoundUserInterface.SendMessage(message)` | Отправляет очередное штатное действие именно этому аппарату |
| `BoundUserInterface.Close/Dispose` и удаление окна | Отменяют сессию, отсоединяют обработчики и запрещают дальнейшую отправку |

Состояние содержит входную и выходную ёмкости, состав буфера, объёмы, режим Transfer/Discard, сортировку и параметры фасовки. Оно не содержит идентификатор входной мензурки и её температуру. Контроллер выполнения привязывается к экземпляру BUI, его `Owner`, `UiKey` и текущему подключению; нельзя выбирать аппарат по названию окна.

В [клиенте SS220](https://github.com/SerbiaStrong-220/space-station-14/blob/86d0f7bffb5f3f4d3ee7bef3b9080c2e37b7ec03/Content.Client/Chemistry/UI/ChemMasterBoundUserInterface.cs) штатный обработчик реагента создаёт `ChemMasterReagentAmountButtonMessage(ReagentId, Amount, FromBuffer)`. Мод должен создавать тот же тип из уже загруженной `Content.Shared`, сохраняя обычный канал BUI. Собственные сетевые классы потребовали бы поддержки сервера.

Окно уже содержит `TabContainer Tabs`. Предлагаемая вкладка «Рецепты» сохраняет доступ к штатным вкладкам «Вход» и «Выход». Операции над UI и отправка сообщений выполняются в игровом потоке. Расчёт большого плана можно вынести в фоновую задачу на неизменяемой копии данных, а результат применить только при совпадении версии сессии и снимка.

## Что переносить из внешнего помощника

| Текущий код | Решение |
| --- | --- |
| `ChemistryPlanning.cs` | Использовать алгоритмы зависимостей, запасов, катализаторов и нескольких целей; передавать каталог явно |
| `ChemistryVirtual.cs` | Использовать симуляцию конкурирующих реакций, подбор порядка, партий и ограничения вместимости; отделить геометрию и кнопочный ввод |
| `ExecutionSequencePlanner.cs` | Использовать make/ensure, абсолютную цель и ожидаемые состояния; расширить снимок температурой и набором доступных доз |
| `RecipeCatalogService.cs` | Сохранить поиск и категории; заменить обязательную wiki revision источником прототипов текущего подключения |
| `AssistantModels.cs`, `ChemMasterModels.cs` | Выделить независимые модели рецепта, плана и состояния аппарата |
| `ChemMasterExecutor.cs` | Перенести полезные состояния и семантику отмены; сделать новый исполнитель сообщений |
| `MainForm.cs` | Переписать на контролах Robust UI |
| ClrMD reader, ClientDiscovery, WindowsGameInput, calibration, GlobalEmergencyHotkey | Исключить из игрового мода |

Ядро сейчас не полностью независимое: `ChemistryVirtual` ссылается на типы калибровки, а `ChemistryPlanning` и модель реакций используют `Lazy` и файлы возле `AppContext.BaseDirectory`. Нужны явные входные данные каталога, правил, доступных команд и температуры. `AppContext.BaseDirectory` внутри игры относится к игровому процессу. Кроме того, Bootstrap загружает мод из потока байтов: нельзя рассчитывать на путь `Assembly.Location` мода как на директорию его ресурсов.

В текущем `ChemMasterExecutor.cs:15` свойство `RelaxedChemistryChecks` всегда возвращает `true`. Условия, защищённые `!RelaxedChemistryChecks`, включая ряд строгих сравнений состава, обходятся. Поэтому описание проверок в README нельзя принимать за точное поведение этого commit. Новый исполнитель должен явно проверять наблюдаемый результат операции.

## Каталог текущего сервера

Принятое решение: источник правил приготовления — загруженный `IPrototypeManager` текущего подключения, прежде всего `ReactionPrototype` и `ReagentPrototype`. Это позволяет учитывать различия рецептов между серверами. Штатный `GuideReagentEmbed` в локальных исходниках уже перечисляет реакции для реагента. Из прототипов можно построить граф производства, взять локализованные названия и теплоёмкости. Поля реакций описаны в [ReactionPrototype SS220](https://github.com/SerbiaStrong-220/space-station-14/blob/86d0f7bffb5f3f4d3ee7bef3b9080c2e37b7ec03/Content.Shared/Chemistry/Reaction/ReactionPrototype.cs).

Каталог фиксируется на сессию с отпечатком нормализованных правил. При смене сервера или перезагрузке прототипов план теряет актуальность. Wiki-каталог можно сохранить для пользовательских категорий и подсказок, но коэффициенты приготовления должны соответствовать правилам подключения. Наличие клиентского прототипа не доказывает отсутствие дополнительной серверной логики: фактический состав после действия остаётся обязательной проверкой.

Сохранённые наборы содержат цели и количества, а не закреплённую последовательность ингредиентов и команд. При их загрузке на другом сервере мод проверяет наличие реагентов и строит новый план по текущему каталогу. Отсутствующие цели или неподдерживаемые реакции показываются пользователю до запуска. Если получить или разобрать актуальные правила нельзя, автоматическое приготовление недоступно; подмена правилами SS220 из старого JSON запрещена.

Учитываются все доступные реакции, а не только выбранный рецепт: приоритет, порядок, катализаторы, quantized, температурные границы, теплоёмкости, требуемые аппараты и эффекты. Неподдерживаемый эффект или операция требуют явного ограничения плана; нельзя считать их обычным смешиванием.

Текущие JSON привязаны к SS220. Локальная upstream сборка, использованная для проверки API, имеет другой набор правил. Нельзя проверять рецепт SS220 по одному клиенту, а затем заявлять совместимость со всеми форками.

## Команды и точность объёма

Объём переноса — перечисление, а не произвольный `FixedPoint2`. В проверенной локальной DLL доступны `1, 5, 10, 15, 20, 25, 30, 50, 100, All`. В закреплённой [схеме SS220](https://github.com/SerbiaStrong-220/space-station-14/blob/86d0f7bffb5f3f4d3ee7bef3b9080c2e37b7ec03/Content.Shared/Chemistry/SharedChemMaster.cs) дополнительно есть `75`. Набор доз необходимо обнаруживать при подключении: исходный симулятор помощника содержит 75 в фиксированных списках.

Значение 0.01u в модели не означает возможность отправить такую дозу. [Сервер SS220](https://github.com/SerbiaStrong-220/space-station-14/blob/86d0f7bffb5f3f4d3ee7bef3b9080c2e37b7ec03/Content.Server/Chemistry/EntitySystems/ChemMasterSystem.cs) отвергает значения вне перечисления. Перенос ограничивается реальным запасом и свободной вместимостью; поэтому `All` либо частичный остаток могут давать дробный результат, но не служат универсальной командой точного дозирования.

План должен показывать фактический выход и избыток. Пример из существующей модели: для цели 5u диловена с тремя равными исходниками приготовление целыми дозами может дать 6u из 2+2+2. Возможность получить точную цель нужно доказывать конкретным планом; округление нельзя скрывать.

В адаптере сохраняется полный `ReagentId`, включая `Data`, а не только строка `Prototype`: кровь и другие реагенты могут иметь разные дополнительные данные. Для расчётов допустимо агрегировать совместимые варианты, но исполнитель должен выбирать конкретные строки из свежего состояния. Неоднозначность нельзя разрешать случайным выбором.

## Температура и замена мензурки

Базовый сценарий использует BUI для состава. Дополнительный путь в локальных исходниках — найти входной предмет через `ItemSlotsSystem`/контейнер и прочитать его раствор через клиентский `SolutionContainerSystem`.

`SolutionComponent` сетевой, содержит `Solution.Temperature`; `SharedSolutionContainerSystem.OnSolutionGetState/OnSolutionHandleState` передаёт и клонирует раствор. Это подтверждает возможность такого адаптера на уровне исходников, но доступность нужной solution entity и своевременность температуры при открытом химмастере требуется проверить на целевом сервере.

Если температура и идентификатор ёмкости доступны, использовать их для проверки температурных этапов и обнаружения замены мензурки. Если нет — показывать неизвестную температуру, запрашивать подтверждение холодной/горячей мензурки и сохранять ограничения двухфазной схемы. Одинаковое название, объём и состав не доказывают, что ёмкость не заменили.

Нагреватель, центрифуга и электролиз требуют собственных адаптеров. Изменение локального компонента температуры не изменит авторитетную серверную химию.

## Выполнение с подтверждением результата

Предлагаемые состояния: `Idle → Planning → Ready → Running → AwaitingState → Completed`. Отклонения переводят сессию в `Paused`, `AwaitingUser` или `Failed`; отмена запрещает новые команды, но уже отправленная операция может завершиться.

1. Получить свежий снимок, проверить ёмкость, состав, цель и совместимость. Если включён Discard, отправить переключение в Transfer и дождаться его подтверждения.
2. Перед очередной операцией сверить химическое состояние и идентичность сессии с последним подтверждённым снимком.
3. Отправить ровно одну команду из плана и запомнить ожидаемый переход.
4. Получать новые `UpdateState`, пока не наблюдается подходящий итог после переноса и реакций. Повторный или промежуточный update сам по себе не является подтверждением.
5. После подтверждения поставить следующую операцию в очередь игрового потока. Не отправлять всю цепочку рекурсивно из `UpdateState`.
6. При таймауте или несовпадении остановиться и сопоставить текущий состав с планом. Отсутствие подтверждения не разрешает повторять уже отправленную команду.

В протоколе нет идентификатора команды с отдельным подтверждением. Ожидаемый состав — наблюдаемое подтверждение, которое не всегда позволяет отличить вмешательство другого игрока. Нужны проверки доступной идентичности, промежуточных переходов и отказ при неоднозначности.

Таймаут обслуживается игровым таймером или обновлением контрола, даже если новые State не приходят. Закрытие окна, отключение от сервера, смена персонажа/аппарата, потеря доступа и отмена инвалидируют очередь. При make остаток считается от зафиксированной абсолютной цели, чтобы перепланирование не произвело исходный заказ повторно.

## Предлагаемый интерфейс

- Список препаратов с поиском, категориями и количеством для каждой цели.
- «Приготовить ещё» и «Довести запас до» вместо обязательного знания терминов make/ensure.
- Сохранённые наборы с именем, целями и количеством; версия формата и отпечаток каталога проверяются при загрузке.
- Предпросмотр ингредиентов, недостачи, порядка действий, партий, фактического выхода и ручных этапов.
- «Начать», «Пауза», «Продолжить», «Стоп», текущая операция и подтверждённый прогресс.

Сохранённая смесь проходит ту же симуляцию: выбранные компоненты могут вступать в реакцию. Изменение целей инвалидирует предпросмотр. «Стоп» остаётся доступным при выполнении, а конфликтующие штатные действия с аппаратом приостанавливают автоматизацию.

Предлагаемое хранилище: `%LOCALAPPDATA%/SS14LocalMods/ChemMaster/recipes.json`. Наборы остаются после закрытия окна; исполняемая сессия не возобновляется автоматически после переподключения.

Фасовку в таблетки и бутылки лучше добавлять после стабильного приготовления. Штатные сообщения уже есть, но надо проверять выходную ёмкость, источник DrawSource, дозировку, число таблеток, состав и длину этикетки. При фасовке из общего буфера извлекается смесь; получение чистого отдельного препарата требует отдельного плана размещения и проверки.

## Размещение в ModLauncher

Предлагаемая структура:

```text
ChemMaster/
  ChemMaster.csproj          # ChemMaster.Mod.dll, net10.0
  Mod.cs                    # Install и проверка игрового API
  GameChemistryAdapter.cs    # прототипы, State, полные ReagentId
  ChemMasterSession.cs       # выполнение и ожидание результата
  RecipePanel.cs            # Robust UI
  RecipeStore.cs            # сохранённые цели
  Core/                     # переносимые алгоритмы и модели
ChemMaster.Tests/            # ядро и сценарии выполнения
scripts/Test-ChemMasterApi.ps1
```

На первом этапе ядро можно компилировать исходниками в одну DLL мода, чтобы сохранить нынешний формат установки и независимых обновлений. Для совместного использования с внешним помощником позже выделить общий исходный пакет или закреплённый модуль. Дополнительная Core DLL потребовала бы явно продуманной доставки зависимостей.

Встроенные справочные JSON при необходимости положить в embedded resources. При работе с прототипами сервера они не нужны как источник коэффициентов. Пользовательские рецепты хранятся отдельно от установки.

Добавление нового ID `chem-master` затрагивает `catalog/mods.json`, сборку/payload и описания RU/EN. `Launcher.Core/Catalog.cs` читает встроенный каталог; отдельного жёстко заданного списка ID в текущем рабочем дереве нет. Минимальную версию лаунчера выбрать по фактически выпущенной версии, содержащей новый каталог. Текущую незавершённую работу Death Rattle и её release-настройки учитывать отдельно; уже опубликованные DLL других модов сохраняются по прежним хешам.

## Этапы и критерии проверки

| Этап | Проверяемый результат |
| --- | --- |
| 1. Подключение UI | Вкладка появляется у открытого химмастера; состав соответствует штатному окну; обработчики очищаются при закрытии |
| 2. Каталог и ядро | Каталог строится по подключению; доза 75 используется только при её наличии; простой и составной рецепты имеют проверенный план |
| 3. Выполнение | Одна команда на подтверждённый переход; возврат продукта в буфер; отсутствие повторной отправки при задержке |
| 4. Наборы | Сохранение и загрузка нескольких целей; make/ensure; корректный остаток после паузы и перепланирования |
| 5. Температура | Проверка доступности реплицируемого раствора; корректные ручные этапы, если температура недоступна |
| 6. Фасовка | Подтверждённые таблетки/бутылки с ожидаемым составом |

Для первой рабочей версии достаточно этапов 1–4 с реакциями при обычной температуре. Проверить небольшую мензурку, конкурирующие реакции, нехватку ингредиента, make/ensure при существующем запасе, задержанные/повторные State, частичный перенос, ручное вмешательство, закрытие BUI, переподключение и несколько открытых аппаратов. Отдельно проверить объём и дополнительные данные ReagentId.
